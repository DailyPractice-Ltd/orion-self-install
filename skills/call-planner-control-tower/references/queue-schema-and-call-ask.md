# Live queue schema and clear call ask

Read the live header row before every write. A later insertion added `Call ask — achieve this` immediately after `Blue-collar assessment`. Current Call Queue columns are A Priority, B Company, C Name, D Position, E Direct / mobile, F Company / reception, G Blue-collar assessment, H Call ask — achieve this, I Owner, J Stage, K Dialled, L Connected, M Action Required?, N Outcome / Instruction, O Callback date and time, P Short call note. Supporting tabs have independent schemas.

Resolve by exact header names, not fixed positions. If required headers are absent or duplicated, hold mutations and report the mismatch. Older references to “Column M outcomes” mean the former layout; current M is a checkbox, not an instruction. The Call ask column is generated guidance and never grants send, task, calendar or CRM authority. Preserve and process only the actual user-authored Outcome / Instruction under the existing authorization gates.

## What a useful ask contains

The business owner's standing revision supersedes any earlier two-part script: H is a direct instruction, normally one short line. Do not add example questions, generic pain-point hypotheses, role-based personalization, or an account summary.

Keep essential relationship context visible, not buried in P or behind a source link: `Spoke [date]; video sent · Follow-up — book SQL.` Add a second short line for verified webinar context when relevant: `Registered: [webinar], [date]; attendance unknown.` The action remains direct; removing scripts must not remove the previous conversation. Follow [contact history and re-entry gate](contact-history-and-reentry.md) before calling a row ready.

Use verified conversation context followed by the job to do:

- Current Prospect, qualified Lead or MQL: `Book SQL.`
- Current SQL: `Nurture SQL.`
- Active contract/proposal: `Contract follow-up — get a decision.` Add `negotiate [specific unresolved term]` only when the evidence identifies that term; this is not authority to change terms.
- A specific evidenced next step overrides the generic lifecycle action: `Book the product walkthrough.` or `Agree onboarding with the named champion and the site supervisors.`
- Webinar context may stay as a short suffix: `Book SQL — webinar follow-up.` Signup is not attendance.

Webinar status must be glanceable in H when relevant, with session/date: distinguish `Registered`, `Attended` (verified), `Recording signup; viewing unknown`, `Interest expressed` (actual reply), `3/3 sent; delivery unknown`, and `Invitation scheduled; signup not found`. Do not hide a known signup in P, turn invitation copy into interest, or turn an incomplete search into `not registered`. When sources are inaccessible say `Webinar status unverified`. Match the exact person's email and current employer. No new column is needed; resolve the Call ask header, never overwrite a phone column because someone recalls an old letter.

Where person-level conversation history is verified, prefix `First conversation —`, `Second conversation —`, or `Third conversation —`. Count actual two-way conversations with that person, not dial attempts, unanswered calls, emails, webinars or conversations with colleagues. Reconcile Call History with current CRM/communication evidence, deduplicate the same conversation and verify history completeness before asserting an ordinal. A planned first call or no recorded calls does not prove no earlier conversation. If a prior conversation is evidenced but the lifetime count is not, use `Follow-up — book SQL.` If history is unverified, omit the ordinal and record that limitation in the cell note; never invent a count.

Read current task, latest user outcome/direct communication and current lifecycle before choosing the action. A newer specific human instruction overrides the old purpose, but does not authorise executing it during a wording repair. `Book SQL` is an objective to earn an accepted qualified meeting, not a claim that SQL status already exists or a reason to change lifecycle, priority or eligibility. The call-ranking and SQL evidence gates remain unchanged.

For paying customers and signed trials, require a current, specific customer-facing decision, blockage or approved exception. Lifecycle, historical recovery flags, old target dates or a generic CS check-in alone do not justify a P0 sales call. Check the linked deal and relevant recent evidence before reusing an old recovery ask. Resolve internal reconciliation/admin internally rather than using the salesperson's call to discover what the agent should already know.

Apply [Attio-first queue routing](today-only-queue.md). Remove explicit evidenced wait/hold/do-not-call/skip cases during cleanup; preserve other useful original rows. Do not turn missing due-today tasks, internal planning slots or checked boxes into new removal rules. Reconcile useful missing controls in Attio under current authority; never create a shadow backlog. Preserve human entries before removal. Do not overwrite a new outcome with the old call purpose.

Keep supporting source IDs, deadlines, caveats and account context in Short call note (P), with source evidence in a cell note when useful. Preserve H through row sorts and carry-forward; regenerate it when the next action changes. Do not move the detailed note into H wholesale. Preserve company/assessment hyperlinks and native validation.

## Verification

After a schema change, verify table coverage, owner filters, conditional-format formulas, controls, callbacks and source notes against their original row identities. Update the morning/EOD consumers in place without changing schedule or authority; never change the separate sales-execution task monitor automation. Never run closeout or reset checked boxes as part of a layout-only repair. Read back every new ask and compare all displaced values, links, notes and controls. Resolve concurrent human edits in favour of the newer human entry.
